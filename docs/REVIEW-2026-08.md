## 0. Remediation Status

**All 63 findings in this document are fixed (2026-08-04).** The work went out
as ten tracks with strict file ownership, each fix gated on a regression test
that fails on the prior code (Rule 1 of `docs/IMPLEMENTATION.md`), red-verified
by reverting the fix shape and watching the test fail. Test counts: JS 361 →
604, Rust 43 → 48; `cargo clippy -D warnings` clean; `npm run build:ext` and
`build:sample-rules` clean.

The three P0s were reproduced before being fixed and each now has a test that
fails on the prior code:

| P0 | Fix |
|---|---|
| §3.1 `ALLOW_SITE` wipes the allowlist on a cold worker | reads authoritative storage inside the serialized op, the way `ADD_ALLOWLIST_DOMAINS` already did; the three allowlist mutators join the readiness gate |
| §3.2 interrupted rebuild leaves the index dead and undetected | a `ruleIndexState` marker brackets the destructive window; a surviving marker forces a rebuild, as does a bloom that deserializes empty while sources are indexed |
| §3.3 procedural cache invalidation inverted | the observer walks a bounded ancestor chain when marking dirty — O(8) per mutation rather than O(dirty roots) per lookup — and `init()` starts the observer before the first scan |

Measured outcomes worth recording:

- **1,907 filters recovered** (§4.3). The first-label TLD guard was dropping 1,915, including 35 `@@` exceptions — 16 in unbreak.txt, where a block shipped while the exception written to cancel it was deleted.
- **`$badfilter` goes from 0 to 34 effective suppressions in unbreak.txt** (§4.4). Per-list scope was the one scope in which the feature does nothing.
- **Unknown-scriptlet rate 20.4% → 3.9%** (§5.22), and the counter finally has a consumer, so the next regression is observable rather than silent.
- **Procedural LRU bookkeeping 432 ms → 20 ms per 250k accesses** (§5.15); a full run over 500 elements × 500 rules drops 925 ms → 211 ms and is now flat in dirty-root count.
- **Releases no longer race upstream rotation** (§4.6). The lock was mismatching 6 of 8 lists within 48 hours; the expanded list text is now vendored (7.8 MB, versus 43 MB for the compiled alternative) and the build compiles offline from reviewed snapshots.
- **Six caller-less message handlers deleted** (§5.33), including two that were `SENDER_ANY` — one of which trusted a caller-supplied hostname, resolving half of §4.19 by deletion.

Three findings were fixed differently from the way this document prescribed,
because the corpus contradicted the prescription. They are the interesting ones:

- **§4.23** — the doc said to reject op-first plans outright. 18 legitimate subject-less rules ship today (`##:matches-path(/x/) div.ad`, `##:xpath(…)`), so the seed instead admits document-scoped operators only, and the `:style()` root guard refuses page-*blanking* declarations rather than all root styling, which would have killed ~100 upstream rules that use `:style()` to restore a page.
- **§4.3** — the prescribed one-line host check would have re-admitted `||co.uk^`. The guarantee is kept via the bundled PSL, but only for unscoped patterns, since the corpus ships deliberate `||cloudfront.net^$domain=…` rules.
- **§4.12** — a module-scope guard was not available: `injectIntoOpenTabs` runs a second `executeScript` in the same realm. The marker is a non-configurable `Symbol` brand on the shield's own `JSON.parse` wrapper, honoured only after a behavioural probe with a randomized payload confirms the hook actually works — so forging the brand without doing the shield's job disables nothing.

Known limitation, deliberately left: the **list half** of the §5.25 trust gate is
nominal. User filters — the renderer-reachable vector, via `APPEND_USER_FILTER`
— can never invoke a `trusted-*` scriptlet, which is the half that matters
today. List rules are admitted by list id, but `mergeFilterSources` and
wasm-core's `compile_active_filter_index` both flatten sources, so rules carry
no provenance and the id is absent. Tagging rules at ingestion needs
`src/shared/db.js` and wasm-core together; it is only load-bearing once users
can subscribe to third-party lists.

Also still open by decision, unchanged from the previous cycle: runtime
integrity manifest and release signing, WAR origin scoping for
`scriptlets-world.js`, the `registerContentScripts({world:'MAIN'})` redesign
(§5.38 of the prior review), i18n, `$csp`/`$header=` via `modifyHeaders`, the
redirect resource library, and `chrome.storage.sync` mirroring. `PROC_OPS` now
has three hand-kept copies that agree; unifying them into one shared module is
worth doing before they drift again.

## 1. Executive Summary

The v4.1.0 review found seven ship-blockers that shared one shape: *a feature is silently dead while every observable signal says it is working.* Those are fixed. The remediation was large — nine parallel tracks, test count 165 → 361 (JS) and 27 → 43 (Rust) — and the quality of the individual fixes is high. Several are genuinely exemplary and are named in §6.

The debt moved again, and it moved somewhere predictable: **into the seams between the tracks, and into the new code the tracks wrote.** Three findings are P0, and all three were mechanically reproduced.

1. **One click destroys the user's entire allowlist** (§3.1). `ALLOW_SITE` does its read-modify-write against an in-memory cache that is empty on a cold service worker, and the message gate that would have made it wait does not list it. Seeded with three allowlisted sites, adding a fourth leaves exactly one in storage and one allow rule in DNR — and the UI redraws the truncated list as success.
2. **An interrupted index rebuild is never detected or repaired** (§3.2). The rebuild clears the cosmetic, scriptlet and page-bundle stores, then repopulates across five transactions with no completion marker. Die anywhere in between and the stale bloom filter plus the unchanged rule-data version tell the next startup that everything is fine. All domain cosmetics and all scriptlets are dead — silently, for up to 24 hours, indefinitely if the device stays offline.
3. **Procedural cache invalidation is inverted** (§3.3). `_isInDirtySubtree` asks whether the element is *inside* a mutated subtree, but every operator that reads downward (`has-text`, `has`, `min-text-length`, `semantic`) is evaluated on the *container*, which is an ancestor of the mutation. So the container is dirty only when the insertion is its direct child. The canonical hydration pattern — empty card cached as a miss, ad content inserted below it — leaves the ad visible for the element's lifetime.

Beneath the P0s, three systemic patterns produced most of the P1s:

- **Fixes that stopped at the file boundary.** §5.4 fixed `GET_TAB_STATS` to ignore a caller-supplied `tabId`; `GET_INIT_DATA` and `GET_COSMETIC_RULES` still trust a caller-supplied `hostname` (§4.19). §4.16 taught the options UI to check for `{error: …}` responses; the content script still does not (§4.11). §4.28 moved page-writable "already applied" flags off the global object in three scriptlets; `youtube-shield.js` — the file carrying the headline feature — still has one, and it disables the entire shield (§4.12). §3.3 taught the *build* parser the `$ghide`/`$ehide` aliases; the *runtime* parser, which re-fetches the same list, still drops them (§4.7).
- **Parity work that got one engine.** The static compiler moved to six priority bands; both user-filter compilers stayed on the old four (§4.2). Rust learned to validate bloom payloads; JS did not (§4.8). Rust's allowlist rule builder learned that `allowAllRequests` requires `resourceTypes`; the JS fallback builder did not, and emits a rule Chrome rejects outright (§4.1).
- **uBO argument semantics, at corpus scale.** A fresh 13,759-rule corpus measurement found six scriptlets whose argument handling diverges from uBO in ways that kill or invert rules: 267 `adjust-set-*` rules (79.7% of that scriptlet's corpus), 142 `acs` rules, 103 `aeld` rules, 46 `nowoif` rules, 41 `json-prune` rules, and the whole `no-fetch-if` response-directive vocabulary. §3.8 and §4.34 of the prior review fixed this class in four scriptlets; the same class survives in seven more.

Two things are worth stating plainly in the extension's favour. The security posture genuinely improved: `MESSAGE_SENDER_POLICY` is a real fail-closed gate with an entry for all 27 handled types, and the allowlist validator is layered at four independent choke points including a scrub of already-persisted state. And the diagnostic instinct is now good enough that this review could *measure* rather than guess — the build's drop-sink and skip logs are why §4.3 can say "1,893 filters" instead of "some filters".

**Recommended gate before any further feature work:** §3 in full. All three are small patches — a read-from-storage, a completion marker, and a bidirectional `contains` check — with the largest user-visible impact in the codebase.

## 3. P0 — Ship Blockers

### 3.1 `ALLOW_SITE` on a cold service worker destroys the entire stored allowlist **[verified]**

**Where:** `src/background/service-worker.js:2476-2492` (`allowSite`), `:159` (`cachedAllowlist` init), `:3148-3154` (`needsCache`), `:2529-2541` (`disallowSite`)

`allowSite` computes the new allowlist from the in-memory cache:

```js
return enqueueAllowlistOp(async () => {
    if (cachedAllowlist.has(normalizedDomain)) { ... }
    const newAllowlist = Array.from(cachedAllowlist).concat(normalizedDomain);
    await _rebuildAllowlistStateNow(newAllowlist);
```

`cachedAllowlist` is `new Set()` at module scope and is populated only by `refreshMemoryCache()`, which runs in **stage 2** of `_criticalPromise` — behind WASM init and `ensureRuleDataReady()`. The message listener's readiness gate covers seven message types, and `ALLOW_SITE`, `DISALLOW_SITE` and `SET_ALLOWLIST` are not among them:

```js
const needsCache = message.type === 'GET_COSMETIC_RULES' || ... 'ADD_ALLOWLIST_DOMAINS' || ... 'GET_INIT_DATA';
```

So an `ALLOW_SITE` that is the first message to a freshly-woken worker snapshots an empty set, appends one domain, and `_rebuildAllowlistStateNow` commits that to storage and rebuilds DNR from it.

Reproduced against the harness, seeded with three domains:

```
stored before:       ["bank.example","mail.example","work.example"]
ALLOW_SITE response: {"ok":true,"allowlist":["news.example"]}
stored after:        ["news.example"]
dynamic allow rules: ["||news.example^"]
```

**Failure scenario:** open the options page or popup, leave it idle past the ~30 s service-worker idle kill, click "Add" on the allowlist. Every other allowlisted site is erased from storage and from DNR. `options.js:337-340` then calls `renderAllowlist(res?.allowlist)`, so the UI redraws the one-entry list as a successful add. `disallowSite` has the mirror bug: against an empty cache `!cachedAllowlist.has(domain)` is true, so it returns `{ok: true, allowlist: []}` without touching storage — a success response for a no-op that the UI renders as an empty allowlist.

What makes this diagnosable is the inconsistency: `addAllowlistDomains` (`:2515-2525`), written in the same remediation pass, correctly reads `await getStorage(StorageKeys.ALLOWLIST)` inside the chained op, and `ADD_ALLOWLIST_DOMAINS` *is* in `needsCache`. The pattern was applied to the new handler and not back-ported to the two older ones.

**Fix:** read `StorageKeys.ALLOWLIST` inside the chained op in `allowSite`/`disallowSite`, exactly as `addAllowlistDomains` does — this removes the cold-cache dependency rather than papering over it. Add the three types to `needsCache` as defence in depth. **Test:** send `ALLOW_SITE` before `whenCriticalReady()` resolves and assert the seeded entries survive.

### 3.2 An interrupted index rebuild is never detected; all domain cosmetics and all scriptlets go silently dead **[verified]**

**Where:** `src/background/service-worker.js:888-982` (`rebuildActiveRuleIndexFromStoredSources`), `:1042-1048` (`ensureRuleDataReady`), `:1330-1362` (`loadBloomFilter`)

The rebuild is a destructive clear followed by repopulation across five IndexedDB transactions and three `chrome.storage` writes, with no completion marker:

```js
await db.clearActiveRules();          // :915 — wipes cosmetic + scriptlet + page-bundle stores
...
await db.putBulkCosmeticRules(...);   // :929
await db.putBulkScriptletRules(...);  // :931
...
await setStorage(StorageKeys.BLOOM_FILTER, bloomData);  // :963
```

Die anywhere between `:915` and `:963` — MV3 termination, browser quit, or a `putBulk*` rejection on quota — and the index stores are empty while the **old** bloom filter and the **old** `RULE_DATA_VERSION` survive in `chrome.storage.local`. The startup check keys off exactly those three signals:

```js
if (sourcesReady) {
    if (!existingBloom || !hadSources || ruleDataChanged) { await queueActiveIndexRebuild(); ... }
```

`existingBloom` is present. `hadSources` is true — `clearActiveRules` does not touch `STORE_FILTER_SOURCES`. `ruleDataChanged` is false — the version hashes the *bundled* sources, not the DB contents. **No rebuild is queued.** The stale bloom then reports hits for domains whose rows no longer exist, so every lookup returns an empty bundle.

Reproduced (boot → verify → `db.clearActiveRules()` → boot again):

```
run1 cosmetic for example.com: [".site-ad"]
run1 scriptlets:               [abort-on-property-read, noeval]
run2 cosmetic for example.com: []
run2 scriptlets:               []
run2 hasFilterSources:         true      <- so no rebuild is triggered
```

**Failure scenario:** the 24 h `ALARM_FILTER_UPDATE` fires, `checkFilterListUpdates` spends 30–60 s fetching eight multi-megabyte lists, then calls `queueActiveIndexRebuild()`. The user quits the browser during the rebuild. Recovery happens only on the next *successful* 24 h update or a manual ruleset toggle — up to 24 hours of completely dead cosmetic and scriptlet filtering, indefinitely if the device stays offline. Network blocking still works, which is exactly what makes it invisible.

Two adjacent gaps share the root cause — nothing ever health-checks the index:

- `WasmBloom.deserialize_from_json` (`wasm-core/src/lib.rs:140-160`) deliberately degrades to an *empty filter* rather than throwing on malformed input. `loadBloomFilter`'s try/catch therefore never fires, and `checkBloomFillRatio` sees ratio 0 and does nothing. Same total silence.
- The one caller that could surface a rebuild failure logs to the console instead of the error report: `scheduleActiveIndexRebuild` at `:2843-2844` uses `console.error`. `GET_ERROR_REPORT` keeps reporting a healthy extension.

**Fix:** write `RULE_INDEX_STATE = 'building'` (with the target version) to `chrome.storage.local` immediately *before* `db.clearActiveRules()`, clear it only after the last write, and treat a surviving marker as `ruleDataChanged` on startup. Cheaper interim mitigation: after `loadBloomFilter`, if `hasFilterSources()` is true but a known-populated key returns nothing — or the bloom's fill ratio is 0 — force a rebuild. Route `scheduleActiveIndexRebuild`'s catch through `reportError`.

### 3.3 Procedural cache invalidation is inverted — subtree-reading operators serve a stale verdict for the element's lifetime **[verified]**

**Where:** `src/content/cosmetic-engine.js:565-575`, consumed at `:551-554`; observer at `:953-961`

```js
_isInDirtySubtree(el) {
  const roots = this._lastDirtyRoots;
  if (!roots || roots.length === 0) return false;
  for (const root of roots) {
    if (root === el) return true;
    if (root.contains && root.contains(el)) return true;   // root ⊇ el only
  }
  return false;
}
```

The check asks "is `el` **inside** a mutated subtree". But every operator that decides its verdict by reading *downward* — `has-text`, `min-text-length`, `has`/`if`/`if-not` (`:652-677`), `semantic` — is evaluated on the **container**, whose truth changes when content is inserted *below* it. The mutation record's `target` is the inner node, so the container is an *ancestor* of the dirty root and `root.contains(el)` is false. The observer only ever records `mutation.target` and the added nodes; it never walks up. The container is therefore dirty **only when the insertion is its direct child**.

Reproduced:

```
initial verdict (expect null): null
after mutation, dirty roots = [p, span]
verdict for container (SHOULD be container, got): null
BUG CONFIRMED: true
control (container itself dirty): true
```

**Failure scenario:** a framework card (`ytd-rich-item-renderer` and its equivalents) is created empty. Procedural run #1 evaluates `:has-text(Sponsored)` → miss, cached. Hydration then fills `#content > ytd-ad-slot-renderer` inside it. `mutation.target` is the inner container; the card is not dirty; the stale miss is served. Nothing ever clears it — `_matchCache` is cleared only by the SPA `matches-path` sweep (`:410-415`, which is key-prefixed) and the dirty-roots overflow path (`:970-977`); `_startCacheSweep` (`:1024-1031`) resets `_lastDirtyRoots` and trims `_cacheAccessOrder` but never touches `_matchCache`. The ad stays visible for the element's lifetime.

Note the perverse severity gradient: above the 1,000-root cap the overflow path clears the whole cache and recovers, so the bug is worst on *ordinary* pages. And the repo's own §5.28 regression test (`cosmetic-engine.test.mjs:412-427`) asserts the text node's *direct* `parentElement` is dirtied — the one shape where the bug does not bite.

**Fix:** make the dirty test bidirectional for subtree-reading operators (`if (el.contains?.(root)) return true;` alongside the existing check), or — cheaper and O(1) per mutation — have the observer walk a bounded ancestor chain (say 8 levels) from `mutation.target` into `_dirtyRoots`. Two ordering bugs deserve fixing in the same patch: route the `DOMContentLoaded` re-run (`content-main.js:86-88`) through `_scheduleProceduralRun()` so it swaps the dirty snapshot rather than running against a stale one, and move `_applyAllProcedural()` (`:348`) *after* `_startObserver()` (`:351`) so mutations during the first scan are recorded.

## 4. P1 — Correctness

### 4.1 The JS allowlist rule builder emits an `allowAllRequests` rule Chrome rejects **[verified]**

**Where:** `src/background/service-worker.js:2562-2571` vs `wasm-core/src/lib.rs:747-767`

The Rust builder was fixed to satisfy Chrome's constraint that `allowAllRequests` **must** declare `resourceTypes` limited to `main_frame`/`sub_frame`. The JS fallback — which runs exactly when `wasmReady` is false — was not:

```js
newRules = normalizedAllowlist.map((domain, i) => ({
  id: DNR_ALLOWLIST_START + i,
  priority: 500,
  condition: { urlFilter: `||${domain}^` },   // no resourceTypes
  action: { type: 'allowAllRequests' },
}));
```

**Failure scenario:** WASM init fails — the exact situation a fallback exists for — and the user has, or adds, an allowlist entry. `_rebuildAllowlistStateNow` sets `cachedAllowlist` and commits storage *before* `rebuildAllowlistRules` throws, so `IS_SITE_ALLOWED` reports "allowed", cosmetics and scriptlets are disabled for the site, and the popup shows the site as paused — while DNR never received the allow rule and network blocking stays fully active. On the next startup the §4.7 reconcile detects the count mismatch, retries, and throws again, failing stage 2 of `_criticalPromise` so `_criticalReady` is never set.

The harness runs with WASM permanently unavailable, so `sw-allowlist.test.mjs` exercises this exact builder — but the stub's `updateDynamicRules` (`chrome-stub.mjs:118-146`) validates ASCII `urlFilter` and RE2 compatibility while omitting the `allowAllRequests` rule, so the invalid shape passes.

**Fix:** add `resourceTypes: ['main_frame', 'sub_frame']` to the JS builder; add the corresponding validation to the stub so either builder regressing fails a test; ideally assert both builders emit identical objects for the same input.

### 4.2 User-filter DNR priorities were never migrated to the six-band scheme

**Where:** `wasm-core/src/lib.rs:1225-1237` vs `scripts/build-rules.mjs:868-875`; JS fallback at `src/background/service-worker.js:2451-2456`

The build track landed six bands — `BLOCK 1, REDIRECT 2, ALLOW 3, IMPORTANT_BLOCK 4, IMPORTANT_REDIRECT 5, IMPORTANT_ALLOW 6`. The runtime user-filter compiler fixed §4.10's *relative* inversion but kept the old numbering, while its comment claims parity:

```rust
// "Matches DNR_PRIORITY in scripts/build-rules.mjs"  <- no longer true
(true, true)  => 4u16,   // @@...$important
(true, false) => 2u16,   // @@...
(false, true) => 3u16,   // ...$important
(false, false) => 1u16,  // plain block
```

Dynamic and static rules compete on the same numeric scale, with ties broken by action precedence (allow > block > redirect), not by ruleset. Two inversions follow:

- A user's `||x^$important` (3) against a list's plain `@@||x^` (ALLOW = 3) ties, and the allow wins on action precedence. This is §4.10's defect — marked fixed — alive again across the seam. The static scheme puts `IMPORTANT_BLOCK` at 4 precisely so it beats `ALLOW` at 3.
- A user's `@@||x^$important` (4) loses to a list's `$important,redirect=` (5). Statically, `IMPORTANT_ALLOW = 6` exists to prevent exactly this.

The SW's JS fallback compiler disagrees with the WASM one it falls back from: plain exception 3 vs 2, and no important band at all.

Both engines' priority tests assert only *relative* order within their own compiler, and `tests/parser-parity.test.mjs` reduces network rules to `{kind: 'network'}`, discarding priorities — so nothing compares the two scales.

**Fix:** renumber the Rust match to `(1, 3, 4, 6)` and `parseSimpleNetworkRule` to `(1, 3)`; add a cross-seam test asserting the user compiler's band for each `(exception, important)` pair equals the static `DNR_PRIORITY` band.

### 4.3 The TLD guard fires on the first *label*, dropping 1,893 legitimate filters including 16 unbreak exceptions **[verified]**

**Where:** `scripts/build-rules.mjs:1108-1114`

```js
const labelMatch = /^\|\|([^.|/*?^]+)/.exec(pattern);
if (labelMatch && KNOWN_TLDS.has(labelMatch[1].toLowerCase())) {
  reportDrop(`urlFilter: ||${labelMatch[1]}^ anchors on TLD ...`);
```

The regex captures only up to the first dot, so any pattern whose first *subdomain label* collides with a TLD name (`app`, `tv`, `dev`, `me`, `my`, `ca`, `cc`, `co`, `at`, `id`, …) is rejected as "anchors on TLD" despite anchoring on a full multi-label host. Measured against a fresh corpus:

| list | TLD-drops | of which multi-label (false) | of which `@@` exceptions |
|---|---|---|---|
| easyprivacy | 1,825 | **1,823** (~3.3% of its network rules) | 0 |
| easylist | 42 | ~30 | 0 |
| ubo-filters | 19 | 13 | 0 |
| ubo-unbreak | 17 | 17 | **16** |

Confirmed drops include the major mobile-attribution trackers — `||app.adjust.com^`, `||app.link/_r?` (Branch), `||app.clickfunnels.com/cf.js` — and, worse, unbreak *exceptions* for `dev.visualwebsiteoptimizer.com` and `cc.naver.com/cc`: the EasyPrivacy block ships while the exception written to unbreak it is deleted, producing over-blocking with no list-level escape.

**Fix:** reject only when the entire host portion is a single TLD label — capture `/^\|\|([^|/*?^:]+)/` and drop only if `!host.includes('.') && KNOWN_TLDS.has(host)`. Regression vectors: `||com^` still dropped, `||app.link^` and `@@||dev.visualwebsiteoptimizer.com^` kept.

### 4.4 `$badfilter` is scoped per-list, so the list that actually uses it gets zero effect **[verified]**

**Where:** `scripts/build-rules.mjs:1177-1197` (`applyBadfilterSuppression`, called per-list from `parseFilterList`)

The implementation is correct; its scope is not. The design note claims "in practice list authors target their own list's rules." Measured:

| list | badfilters | suppressed in-list | exact matches in *another shipped list* |
|---|---|---|---|
| ubo-filters | 29 | 1 | 3 |
| ubo-unbreak | 204 | **0** | **34** |

unbreak.txt's `$badfilter` entries exist precisely to cancel *other* lists' breaking rules — `||sumo.com^$badfilter` against EasyPrivacy's `||sumo.com^`, plus `||exoclick.com^`, `/ga_setup.js`, `/api/v1/metrics`, `||bridgetrack.com^`. All 204 are consumed as no-ops and the breaking blocks stay live. The two-pass machinery works at the wrong granularity, so the primary real-world consumer of the feature gets ~0% of it.

**Fix:** two-phase build — parse all lists, collect badfilter canonical keys corpus-wide, then suppress during each list's conversion. uBO scopes to enabled lists; corpus-wide is the closest static approximation and errs toward fewer broken sites. (Separately, uBO supports subset-`$domain=` badfilters that *narrow* a rule; exact-match cannot express those. Zero current hits.)

### 4.5 `system-unbreak` blocks at priority 1100 override the user allowlist at 500 **[verified]**

**Where:** `rules/system-unbreak.json` ids 11, 100, 101, 102 vs `src/background/service-worker.js:2565`

The build's own band documentation asserts that the allowlist's `allowAllRequests` "sits far above all of these at priority 500, and system-unbreak at 1000". Four system-unbreak entries are **blocks at 1100**: `youtube.com/youtubei/v1/ad_break`, `datadome.co`, `fingerprintjs.com`, `fpjs.io`.

**Failure scenario:** a DataDome-protected site (Leboncoin, Foot Locker, …) misbehaves. The user adds it to the allowlist — the extension's advertised "trust this site" control — and `datadome.co` requests are *still* blocked at 1100, so the CAPTCHA loop persists. `prevent-fetch.js:40-61` has a full `parsePropsToMatch` with a known-props table; `prevent-xhr` treats the whole string as one URL pattern. uBO shares one parser between both. **8 of 227 rules** use the `key:value` form (`method:HEAD`, `url:googlesyndication`) and match only URLs containing that literal substring — never. A further **11 rules** pass a `directive` argument that is not in the signature at all, so every blocked request returns `''`.

**Fix:** lift `parsePropsToMatch` into `shared-utils.js` and have both call it with `url` as the implicit key.

## 5. P2 — Hardening

### Service worker

**5.1 `FORCE_CLEAN_ALL_DYNAMIC_RULES` leaves `USER_FILTERS_APPLIED` intact** (`:3386-3395`), so the startup short-circuit means user-filter DNR rules never come back. It has no UI caller, which is the only reason this is P2.

**5.2 `CONTENT_BLOCKED` puts no upper bound on `count`** (`:3445-3446`). `Number.isFinite(1e308)` passes, so a hostile page can drive `totalBlockedToday` to a nonsense value that is then persisted to storage and the session mirror.

**5.3 `CHECK_FILTER_UPDATES` returns `{ok: true}` on total failure** (`:3397-3400` vs `:1831-1834`). When all eight fetches fail (offline), `checkFilterListUpdates` bails early and the handler still reports success; the options page then reads a `lastUpdateCheck` that was never written and shows no error. "Update All" while offline is a silent no-op. The same handler returns `{ok: true}` instantly when an update is already in flight.

**5.4 The §5.3 rebuild guard is a live check, not a generation compare** (`:3562`). Persistence is gated *after* the bundle promise resolves, so a lookup that starts before a rebuild and resolves after it still persists a bundle computed against pre-clear state — and `setCachedDomainRules` (`:3557`) writes it to the in-memory cache the rebuild just cleared, unconditionally. Separately, `_activeIndexRebuildDepth` is decremented only in a `.finally()`, so a rebuild that never settles pins the counter above zero forever, permanently disabling page-bundle persistence *and* blocking every future queued rebuild.

**5.5 The user-filter size cap counts UTF-16 code units server-side** (`:3320`, `:2412`) while `options/messaging.js:20` and `wasm-core/src/lib.rs:297` both count UTF-8 bytes. A 1.5 M-character non-ASCII list passes the SW check and fails the Rust one; `compileUserFiltersViaWasm` catches the throw and returns `null`, which is indistinguishable from "WASM unavailable" — so the naive fallback runs on the whole blob without the critical-path guard. That is §5.14's failure mode reachable purely from input.

**5.6 `parseSimpleNetworkRule` is a fourth, unhardened filter parser** (`:2421-2457`). Sprint 3 unified three parsers with fail-closed unknown-modifier handling and left this one out. Executed: `$badfilter` → active block, `$removeparam` → domain block, `@@…$ghide` → §3.3's blanket network-allow verbatim, `$important` silently dropped. Scope is user filters on the WASM-down path only, but users routinely paste list snippets, and behaviour changes with WASM health, invisibly.

### Shared libraries

**5.7 One failed lookup poisons the whole coalesced cosmetic batch** (`db.js:246-256`). A request `error` event that is not `preventDefault()`ed aborts its transaction; the handler rejects only the failing entry and lets the error propagate, so `rejectAll` rejects every sibling. Pre-coalescing, a single-record failure was confined to one lookup; now the whole ancestor walk rejects and the page gets *no* cosmetic rules. Fix: `event.preventDefault(); event.stopPropagation();` in the per-request handler.

**5.8 A truncated binary bundle decodes as a silent partial rule set** (`rule-transport.js:73-95`). `readStringList` returns whatever it accumulated, so `decodeBinaryRules` always returns truthy and the documented JSON fallback can never fire for structural damage. Verified: a truncated payload loses the `.keep` exception entirely and leaks a half-JSON string into `domainSpecific` as a bogus selector. Also, `planVersion` is written by Rust on every rule and `grep -rn planVersion src/` returns nothing — the §5.21 versioning fix shipped with no consumer.

**5.9 Fetch bounds are per-request, not per-list** (`filter-parser.js:241-349`). The 25 MB cap applies per call while `!#include` sub-fetches run in parallel to depth 5, so a hostile list can hold N×25 MB at once. `includePath.startsWith('http')` accepts `http://` includes inside an HTTPS list, sidestepping the redirect guard. And the joined text can exceed Rust's 16 MB ingestion cap while passing the JS cap, at which point the whole list is dropped with one console line.

**5.10 `!#include` fetch failures fail open** (`build-rules.mjs:257-261`), quietly narrowing the very text the SRI hash covers. A *persistent* failure is skipped identically during hash generation and during the build, so the truncated corpus hashes consistently and ships verified. An on-path attacker who can consistently break one sub-file URL achieves silent content removal despite SRI.

**5.11 `ancestorDomains` breaks its own contract on unnormalized input** (`psl.js:67-75`). `'bbc.co.uk.'` walks to `'uk.'` and `'WWW.EXAMPLE.COM'` walks to `'COM'`. Currently defused because every SW call site normalizes first, but `db.getScriptletRules` takes any string. Separately, the §4.8 exact-membership fix reached `AllowlistMatcher::check` and `allowlistCoversHostname` only, so a rule keyed at a curated suffix (`github.io##+js(…)`) can never apply on that host.

**5.12 The bloom "legacy payload" path re-admits the incompatible 64-bit blooms the format tag was built to refuse** (`lib.rs:150-152`, `bloom.js:76-78`). The stated rationale — "legacy JS payloads used the same hash" — is false for *wasm-produced* legacy payloads, which were the primary path and used the old 64-bit hash with no tag. Mitigated because `ensureRuleDataReady` rebuilds whenever the bundled sources hash changes; the hole is a code-only patch release with unchanged packaged rules.

### WASM core

**5.13 The CSS-safety gate accepts invalid selector shapes** (`lib.rs:1839-1858`). `rest.starts_with(p)` matches `::before2` against `::before` with no boundary check, and nothing rejects a leading combinator: `div::before2`, `div::first-line-x`, `> .ad` and `+js()` all pass. Because up to 100 selectors are joined per rule, one invalid selector invalidates the whole declaration in the browser — 99 legitimate hide rules fail open.

**5.14 JS↔Rust `parseLine` divergences remain on real edge shapes** (verified by driving the shipped artifact): `example.com##+js(foo) extra` is a cosmetic selector in JS and a **live scriptlet** in Rust; `EXAMPLE.com##.Ad` is keyed case-sensitively in JS (dead) and lowercased in Rust (live); `example.com#?#div:has-text(/ad;box/)` survives JS ingestion and is dropped by Rust's semicolon rule. Which rules a user gets depends on whether WASM initialized.

### Content scripts

**5.15 `_recordCacheAccess` is the dominant cost of every procedural run** (`cosmetic-engine.js:528-535`). It does `indexOf` + `splice` on a 500-entry array, once per element per operator step, though the key is per-*rule*. Measured: 485 ms per 250k lookups; a single run over 500 candidates × 500 rules blocks the main thread for **>1.3 s** on a 100 ms debounce. The correct pattern already exists 40 lines below in `_getSemanticVerdict` — Map insertion order gives O(1) LRU. Also hoist the call out of the per-element path.

**5.16 `showErrorInDialog` destroys the picker's own button listeners** (`element-picker.js:844-849`). `footer.innerHTML +=` re-parses the footer, replacing the Cancel and Create buttons with fresh nodes. The §5.30 shadow-DOM refusal calls this function — so the user reads "pick the outer element instead", picks it, clicks Create, and nothing happens.

**5.17 Picker keyboard and pointer events leak to the page** (`element-picker.js:238-246`, `:211-236`). Only `Escape` is intercepted, and the dialog has no focus trap — typing a selector on YouTube fires the page's `k`/`j`/`space`/`f` shortcuts. Only `click` is suppressed, not `mousedown`/`pointerdown`, and the overlay is removed on first click, so subsequent presses reach the page's own handlers.

**5.18 `characterData` gating misses text operators nested inside `:has()`** (`cosmetic-engine.js:339-342`). The scan checks top-level `step.op` and never the argument, so `div:has(span:has-text(Ad))` — a very common uBO shape — yields `_hasTextRules === false` and the §5.28 fix does not apply to it.

**5.19 `_lastDirtyRoots` pins up to 1,000 detached elements for five minutes** (`:1002-1003`, `:1024-1031`). Removed nodes are dirty roots, and the array is strong; if mutations stop, only the 5-minute sweep clears it. `stopObserver()` has no production caller — the engine instance is a local `const` in `main()`, so nothing outside it can ever stop the observer or the interval.

**5.20 Planner-parity divergences.** `content-main.js:74`'s `PROC_TOKEN_REGEX` omits `semantic`, so a string-form `div:semantic(x)` rule never constructs the engine (latent — the WASM path delivers objects). The SW's fallback `PROC_OPS` (`:466-482`) also omits `semantic`, so in the WASM-down path that selector passes `isSafeCssSelector` and is emitted as **CSS**, silently dropping the rule. And `parseProceduralPlan('div:has-text(Ad')` yields `arg: "A"` rather than rejecting — a malformed line becomes a different, valid rule.

### Scriptlets

**5.21 Detectability: the §5.34 own-property leak was moved, not removed** (`bot-stealth.js:54`). The `WeakSet` correctly replaces `__nullifyPatched`, and the next line assigns an own `toString`. `Object.keys(getParameter)` returned `["__nullifyPatched"]` before and returns `["toString"]` now — both one-line detectors — plus `fn.toString.toString()` returns arrow-function source and `fn.name` is `"wrapped"`. Fix: one shared masking helper backed by a `WeakMap<wrapper, nativeSource>`, plus `name`/`length` copied via descriptors.

**5.22 Residual unknown-scriptlet rate is 20.4% (2,804 of 13,759), and `getUnknownScriptlets()` has no consumer.** The §3.6 counter works but nothing in the SW, popup, options page or build reads it, so the misses are invisible in production. **1,155 rules (8.4% of the corpus) are recoverable by registry aliases alone**: `trusted-set-cookie` 951, `trusted-set-local-storage-item` 176, `json-prune-xhr-response` 18, `trusted-set-session-storage-item` 10. Implementing `rmnt` (831) and `rpnt` (250) would take resolution past 96%.

**5.23 `set-cookie` has no value gate and double-encodes pre-encoded values** (`set-cookie.js:2-7`). uBO's untrusted variant refuses any value outside a fixed safe list or integer range — that restriction *is* the trust boundary between `set-cookie` and `trusted-set-cookie`. 3 of 156 shipped rules carry values uBO would refuse. Unconditional `encodeURIComponent` also mangles already-encoded values (`%5B%22required%22%5D` → `%255B%2522required%2522%255D`).

**5.24 `remove-cookie` issues one delete variant where uBO issues six to eight** (`remove-cookie.js:11-18`). A cookie is deletable only by a `Set-Cookie` whose domain and path match its creation attributes; consent and tracking cookies are overwhelmingly set at the registrable domain. A host-only `path=/` delete does not remove them.

**5.25 `trusted-*` scriptlets remain reachable from any subscribed list and from user filters.** No trust gate exists anywhere (`grep` for `requiresTrust`/`isTrusted` finds nothing). `trustedSetConstant` does `JSON.parse(value)` and installs the result on an arbitrary window path; `trustedReplaceFetchResponse` rewrites arbitrary response bodies. Today the only sources are uAssets, but a third-party list or the picker's `APPEND_USER_FILTER` path reaches both. Fix: carry uBO's `requiresTrust` flag in the registry and filter at spec-build time.

**5.26 Assorted uBO semantic gaps.** `remove-class`'s default selector uses only the first token; `spoof-css` handles one property pair where uBO is variadic (2 of 4 rules lose arguments); `set-constant` ignores a third argument that 10 rules pass; `no-set-timeout-if`/`no-set-interval-if` support neither `!needle` negation nor uBO's delay ranges (`2000-5000` → `NaN`, never matches); `abort-on-stack-trace` matches the raw `Error().stack` where uBO normalizes frames into `stackDepth:N\tfn url:row:1` tokens, so **35 of 209 rules** write needles against synthesized names (`inlineScript`, `injectedScript`) that cannot match, and it only wraps functions, so 17 rules targeting non-function properties are no-ops.

### Build, release, CI

**5.27 The staged rules swap is not crash-atomic** (`build-rules.mjs:1512-1556`). Promotion is delete-then-rename per file in directory order. A crash mid-sequence leaves `rules/` mixed-generation, breaking the exceptions-hoisted "every enabled prefix is self-consistent" guarantee and leaving a stale `ruleset-counts.json` that the SW's budget fallback trusts. Fix: swap at directory granularity, or rename `ruleset-counts.json` last as a commit marker.

**5.28 Tag names are interpolated into release `run:` blocks** (`build.yml:45, 88, 103, 123-133`). `git check-ref-format 'refs/tags/v4.3.0$(id)'` exits 0, so `$(…)` and `${IFS}` are legal in tag names and execute inside the `contents: write` job. Only users with push access can create tags, so this is hardening rather than a live hole — but it is the canonical documented anti-pattern and the fix is one `env:` block.

**5.29 `$domain=` values ship into `initiatorDomains` unvalidated** (`build-rules.mjs:624-631`). Verified emissions: `$domain=foo.com|` → `["foo.com", ""]`; `$domain=Example.COM` → uppercase verbatim; `$domain=bücher.de` → raw non-ASCII. All three are invalid per the DNR schema and Chrome rejects such rules at indexing. Zero occurrences in today's lists, so this is latent — one upstream typo away from shedding rules.

**5.30 `$removeparam=~x` and `$removeparam=/regex/` ship with literal, dead semantics** (`:651-652`, `:1039-1049`). `~keep` means "strip everything except keep" upstream; the emitted rule strips a parameter literally named `~keep`. Fails dead rather than open, but contradicts the pipeline's own rule of dropping what it cannot express.

**5.31 SW privacy rules at priority 1 are disabled by ordinary list exceptions** (`service-worker.js:1588-1744`). Referer-strip, Set-Cookie-strip, persona UA-spoof, ETag-strip and `upgradeScheme` all sit inside the static band range, so any static `allow` (band 3, or 6 for `$important`) beats them. A filter-list exception expresses "don't ad-block this", not "disable privacy hardening"; persona UA-spoofing becoming per-request inconsistent is itself a fingerprinting signal. Fix: give the privacy rules their own band above 6.

**5.32 The `skippedNetwork`/`skippedRules` and `rejected` honesty fields have no reader.** The SW produces both — with comments explaining they exist "so the UI can say N lines were dropped" — and `grep` finds zero hits in `options.js`/`popup.js`. Save 30 RE2-incompatible lines and the UI still reports "✓ Applied N network and M cosmetic rules"; import an allowlist containing `co.uk` and the rejection vanishes behind "✓ Imported (N sites added)".

**5.33 Docs/code drift.** `docs/RELEASE_CHECKLIST.md:100-101` instructs the releaser to check `GET_ERROR_REPORT` "via the options diagnostic surface" — no such surface exists, and `GET_ERROR_REPORT`/`CLEAR_ERROR_REPORT` have zero callers, so the error funnel is write-only. `:93-94` describes a settings export/import round-trip that does not exist. `src/options/messaging.js:17-19` claims the SW's cap is a byte budget; it is UTF-16 code units (§5.5). And six handlers (`SET_SETTINGS`, `SET_ALLOWLIST`, `GET_COSMETIC_RULES`, `GET_NOISE`, `GET_ANONYMIZED_STATS`, `FORCE_CLEAN_ALL_DYNAMIC_RULES`) have no caller — §5.5 deleted two handlers for exactly that reason, and `GET_COSMETIC_RULES`/`GET_NOISE` sit in `SENDER_ANY` with no consumer.

## 6. What Is Genuinely Well Built

Naming these is not politeness; each is a pattern worth preserving through the next round of changes.

**`MESSAGE_SENDER_POLICY` is a real fail-closed gate.** All 27 handled message types have an explicit entry, the map is consulted *before* any handler work, and the `!== SENDER_ANY` comparison means a missing entry — or a prototype-chain key like `__proto__` — resolves to "extension page required" rather than to permissive. The declarative form is what makes that auditable in one screen.

**The allowlist validator is layered at four independent choke points.** `partitionAllowlistInput` runs at the handler, again in `_rebuildAllowlistStateNow`, again at the last stop before DNR in `rebuildAllowlistRules`, and once more against *persisted* state on startup — so a legacy `co.uk` entry written before the validator existed gets scrubbed rather than resurrected. Layering the same predicate at both the storage and the DNR boundary is the right instinct for a check whose failure mode is a TLD-wide bypass.

**The bloom hash port and its cross-engine golden vectors.** `calculate_hash` is a genuinely bit-identical port — UTF-16 code-unit iteration, wrapping-u32 congruence with JS's shift-then-`>>>0` — and the *same* bit indices are asserted independently in `bloom.test.mjs` and in `lib.rs`, so either engine drifting fails its own half of the pair. That is the correct shape for parity enforcement.

**The boot-key capability handshake is properly layered.** `index.js` validates the seed against the generator's exact shape before registering, refuses to register at all if the page pre-claimed the key, and registers a frozen single-key object as a non-configurable data property; the SW then independently re-verifies that descriptor shape after load and withholds all specs on mismatch. Three controls, each closing a different step of the race, with the reasoning — including *why* the key is deliberately no longer deleted — captured in comments. Unusually disciplined for a mitigation of a deferred design problem.

**`_applyOp`'s fail-closed default plus the per-rule failure budget.** The §4.9/§4.11 work did not just add the missing cases; it made the *unknown* case under-block, capped repeat offenders, and wrote down why ("under-blocking is the recoverable direction"). Together with `safeRegex` and `scopeLeadingCombinator`, that converts a whole class of future planner/executor drift from page-blanking into a logged no-op.

**`dedupeKey` gets both the threat model and the failure direction right.** The key is built from primitives, invoking only internal ToString that page code cannot intercept, and the whole dedupe is wrapped so that a failure sets `key = null` and *proceeds to run the scriptlet*. Fail-open is correct here — a duplicate execution is harmless, a dropped scriptlet is a bypass — and both directions are pinned by tests that sabotage `JSON.stringify`.

**Total drop accountability in the build.** The `_currentDropSink` plumbing and per-list `rules/skipped/*.log` with untruncated source lines are why §4.3 and §4.4 could be *measured*. A converter that can tell you exactly which 1,825 lines it dropped and why is rare, and it is what makes this review's numbers trustworthy.

**`compileUserFiltersViaWasm` distinguishes "succeeded with zero rules" from "failed".** A subtle invariant that is very easy to lose to an innocent `if (!newRules.length)` refactor; the doc comment states it, a test-only override seam makes the otherwise-unreachable branch testable in Node, and both directions are pinned.

## 7. Test Gaps

Ordered by defects-caught-per-line, and chosen so each closes a *class* rather than an instance.

1. **The serializing message-bus fixture — still not built.** The prior review put this first and credited it with catching that cycle's worst defect. Wrap both directions in `chrome-stub.mjs` (`JSON.parse(JSON.stringify(…))` on dispatch and in `sendResponse`). This also makes §4.11-class findings (unchecked `{error: …}` shapes) reachable from the harness.
2. **A cold-worker message suite.** Every message type delivered *before* `whenCriticalReady()` resolves, asserting no state loss. §3.1 and §4.14 are both instances; the harness's habit of awaiting readiness first is what hid them.
3. **A termination-during-rebuild test.** The harness can already boot a fresh instance; add the ability to abandon one mid-rebuild and assert the next boot repairs the index. Catches §3.2 and §5.4.
4. **A corpus conformance suite for scriptlet arguments.** Load the real corpus, feed each rule's literal arguments through the registry, and assert the scriptlet observably acts. §4.9, §4.10, §4.17, §4.18, §4.20, §4.21, §4.26 and §4.27 are all one measurement away from being a red test, and together they are the single largest cluster in this review.
5. **A fourth parity leg that drives the WASM artifact from Node.** Demonstrated during this review — `mod.default({module_or_path: bytes})` works — which retires the parity suite's "Rust cannot be driven from Node" caveat and closes §5.14.
6. **Cross-seam priority assertions.** One table asserting the user-filter compiler's band for each `(exception, important)` pair equals the static band, plus an assertion that no static rule outranks the allowlist priority. Catches §4.2 and §4.5.
7. **A DNR-schema validator in the chrome stub.** `allowAllRequests` requires `resourceTypes`; `initiatorDomains` must be lowercase ASCII with no empty entries. Catches §4.1 and §5.29 at the layer that already validates ASCII and RE2.
